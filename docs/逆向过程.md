# 极验3 滑块逆向过程：从浏览器自动化到纯协议

> 这篇文档记录我实现这个项目的真实过程：**先做出能跑的浏览器自动化版本，再花很长时间把它拆成纯协议版本**。
> 文中提到的错误码和现象都来自实际调试记录。扣代码（反混淆）部分只讲主线，不逐行展开。
>
> 目标站点：<https://demos.geetest.com/slide-float.html>（仅用于学习研究）

---

## 1. 起点：先让一次验证通过

### 1.1 手动版：证明 w3 和轨迹是对的

最开始我没有直接写纯协议，而是先做一个最小闭环：

1. 在浏览器里正常打开 demo，抓包拿到 `challenge` 和 `ss`；
2. 用浏览器插件或本地 HTML 页面手动拖动滑块，录下真实轨迹；
3. 把轨迹、`passtime`、`t` 填进 `w_3.js` 的 `get_w3`，生成 `w`；
4. 把 `challenge` 和 `w` 放进 `cs2.py`，直接发 `ajax.php`。

结果拿到了第一次成功：

```json
{"success": 1, "message": "success",
 "validate": "164769bb64f392bd4a1a0b27e1491a07", "score": "1"}
```

这一步非常关键。它证明了：

- w3 的加密结构是对的；
- 轨迹格式 `[[x, y, time_ms], ...]` 和 `passtime/t` 的用法是对的；
- 滑动距离测得基本正确；
- 服务端在这一层是接受纯 requests 提交的。

也就是说，**剩下所有问题都集中在“challenge / s / cookie 会话”的获取上**，而不是加密或轨迹本身。

### 1.2 自动版：浏览器只负责 setup

手动版能过，但每次都要抓包、手动滑，不可持续。于是有了第一阶段的
`极验3_auto.py`：

- 用 DrissionPage 打开 demo；
- 监听 `api.geevisit.com/get.php`，点击雷达按钮；
- 从响应里拿 `challenge_new`、`s_s`、`gt`；
- 后面的图片下载、轨迹池取轨迹、w3 加密、提交验证仍然用 requests。

这个版本解决了两件事：

1. 不用再手动抓 `challenge_new` 和 `s_s`；
2. 用轨迹池里的真人轨迹替代手动滑动，可以连续跑。

它也是我后面做纯协议版的“参照物”：浏览器里每一步实际发了什么、带了什么 cookie、
返回了什么，都可以对照。

## 2. 转折：为什么不能只靠浏览器

自动版能跑，但依赖浏览器，速度和部署都不理想。我想知道：
**浏览器到底替我们做了哪些事？哪些可以搬到 requests 里？**

于是开始逐项拆：

- 页面加载和初始 cookie；
- `register-slide` 拿 `challenge/gt`；
- w1 → 第一个 `get.php` 拿 `s`；
- w2 → `ajax.php` 做无感验证，拿 `GeeTestAjaxUser`；
- 带 `is_next=true` 的 `get.php` 拿图片、`challenge_new`、`s_s`；
- w3 → 最终 `ajax.php` 提交。

拆的过程中最大的感受是：**不能只复制参数，要复制会话状态。**
很多参数看起来是独立的，实际上和上一步下发的 cookie、challenge 的生命周期绑在一起。

---

## 3. 完整链路与参数生命周期

### 3.1 浏览器里观察到的九步请求

| 步骤 | 请求 | 关键产出 |
|------|------|----------|
| 1 | `demos.geetest.com/slide-float.html` | 初始 cookie |
| 2 | `demos.geetest.com/gt/register-slide` | `challenge`(32位)、`gt` |
| 3 | `apiv6.geetest.com/gettype.php` | `GeeTestUser`（.geetest.com） |
| 4 | `apiv6.geetest.com/get.php?w=w1` | `s` |
| 5 | `api.geevisit.com/get.php?w=w2` | `GeeTestUser`（.geevisit.com），只设 cookie |
| 6 | `api.geevisit.com/ajax.php?w=w2` | `GeeTestAjaxUser`，无感验证 |
| 7 | `api.geevisit.com/get.php?is_next=true` | `bg`、`slice`、`challenge_new`(34位)、`s_s` |
| 8 | 下载图片、还原、测距、取轨迹 | `distance`、`guiji` |
| 9 | `api.geevisit.com/ajax.php?w=w3` | `success` / 错误 |

> 这是**浏览器里**能看到的完整链路。当前纯协议版并没有逐步照抄：
> `get_html` 负责初始 cookie，`get_two_w` 直接走 `ajax.php`，由同一个 `session`
> 承接 cookie；`gettype.php` 和「独立的 w2 get.php」没有单独发。
> 少发请求不一定错，关键是 cookie 和 challenge 的状态要对——这也是我最后收敛出的版本。

### 3.2 两个容易忽略的细节

1. **`challenge_new` 比 `challenge` 多 2 个字符**（34 vs 32）。
   最终 w3 必须用 `challenge_new`，不能再用注册时那个 32 位的。
2. **第 5 步的 `get.php` 只用来设 cookie，不要带 challenge**。
   带了会报 `old challenge`。它和后面的 `is_next=true` 是两次不同的调用。

### 3.3 cookie 链

| 域名 | cookie | 来源 |
|------|--------|------|
| `.geetest.com` | `GeeTestUser` | 第 3/4 步 |
| `.geevisit.com` | `GeeTestUser` | 第 5 步（同名不同域） |
| `api.geevisit.com` | `GeeTestAjaxUser` | 第 6 步 |

这三者不是可选项。纯协议版最容易犯的错，就是用 `requests` 裸请求去拿
`get_pic` 或提交验证，结果 cookie 没带过去，服务端直接判 `forbidden`。

## 4. 踩坑记录：错误码其实是一张分层地图

调试时最好用的不是日志，而是服务端返回的错误码。它们基本对应不同的层：

| 返回 | 含义 | 我最后怎么定位 |
|------|------|----------------|
| `{"success":0,"message":"fail"}` | 业务层失败：距离、轨迹、时间等 | 先检查 `distance`、轨迹终点、`t/passtime` |
| `{"success":0,"message":"forbidden"}` | w 解密 / 会话 / challenge 层 | 检查 `gt` 三处是否一致、`e_e` 是否同一个、cookie 是否跨域带上、`challenge_new` 是否用对 |
| `{"status":"error","error":"param decrypt error","error_code":"error_03"}` | w 结构坏了 | 不要删 w 里的字符；检查 AES/RSA 拼接顺序 |
| `{"status":"error","error":"used captcha","error_code":"error_11"}` | challenge 已被使用/污染 | 重新注册；不要复用 challenge |
| `get_pic` 返回里没有 `challenge` | 跳过了 w2 或 w2 失败 | 按顺序走完第 5/6 步 |
| `old challenge` | 在第 5 步提前带了 challenge | 该步只设 cookie，不带 challenge |

### 4.1 “forbidden 不是距离错”

这是我最重要的一次判断转折。

一开始我以为 `forbidden` 是轨迹不像人、被风控拦了，所以不断换轨迹、调扰动。
但后来发现：

- 用**手动滑动**录下来的真实轨迹，配合浏览器抓的 `challenge_new/s_s`，能过；
- 用同一套轨迹，只把 `challenge_new/s_s` 换成程序自己拿的，就变成 `forbidden`；
- 而且一旦出现 `forbidden`，这个滑块在网页里也不能再用了，再提交会变成
  `used captcha`。

这说明 `forbidden` 发生在**轨迹评分之前**：challenge 或会话已经被判无效，
根本不是“轨迹被检测”。真正的距离/轨迹问题通常返回 `fail`，不是 `forbidden`。

### 4.2 “w 不能为空”

第一个 `get.php` 的 `w` 如果置空，请求本身可能还能返回，但后面拿不到背景图和
滑块图 URL。这个现象很容易误导人以为是图片接口坏了，其实是 w1 没有正确生成。

### 4.3 “参数都对，但还是 forbidden”

我遇到过最难的一段时间：把 `challenge_new`、`s_s`、距离都打印出来，和浏览器
完全一样；轨迹也用手动录制的真实轨迹；w3 也是同一个 JS 生成的，但提交仍然
`forbidden`。

最后发现问题不在单个参数，而在**这些参数是从哪条会话里拿的**：

- `challenge_new` 必须来自本次会话第 7 步的 `get.php`；
- `s_s` 必须和 `challenge_new` 同一次响应；
- w1、w2、w3 必须用同一个 `e_e`；
- 第 5/6 步设置的 cookie 必须带到第 7/9 步；
- 不能拿上一次运行残留的 challenge 复用。

把这几个“生命周期”对齐之后，纯协议链路才稳定下来。

## 5. 扣代码：只讲主线

这部分不逐行讲反混淆，只说每个 w 在做什么。

### 5.1 w2

`get_w_2(challenge, gt, s, e_e)` 的主线：

```text
encry_guiji(轨迹)  →  AES  →  插入 tt  →  $_HCB 编码  →  w2
```

其中：

- `encry_guiji` 把轨迹压成 `(dx, dy, dt)` 的增量序列；
- `tt` 用一个固定数组 `[12,58,98,36,43,95,62,15,12]` 和上一步返回的 `s`
  做位置插入；
- `$_HCB` 是从混淆源码里扣出来、补好环境后能直接调用的编码函数。

### 5.2 w3

`get_w3(challenge_new, passtime, t, guiji, s_s, e_e)` 的主线：

```javascript
oo = {
    lang: "zh-cn",
    userresponse: H_2(t, challenge),          // 距离编码
    passtime: passtime,                       // 轨迹总时长
    imgload: 140,
    aa: encry_2(encry_guiji(guiji), 固定数组, s_s),
    ep: { v: "7.9.3", tm: tm, td: -1 },
    h9s9: "1816378497",
    rp: H(gt + challenge.slice(0, 32) + passtime)
}
w3 = base64(AES(JSON.stringify(oo), e_e)) + RSA(e_e)
```

几个必须对齐的点：

- `t` = 轨迹最后一点的 x；
- `passtime` = 轨迹最后一点的 `time_ms`；
- `userresponse` 和轨迹终点必须是同一个距离；
- `rp` 里的 challenge 用前 32 位。

### 5.3 运行环境

`w_2.js` / `w_3.js` 需要 Node.js 和三个 npm 包：

```bash
npm install node-forge crypto-js jsencrypt
```

Python 侧通过 `execjs` 调用，`e_e` 是每次运行随机生成的 16 位十六进制密钥。

## 6. 图片与轨迹

### 6.1 图片还原

背景图是 312×160 的乱序图：26 列 × 2 行，每个竖条 10×80，源图步长 12px、
左偏移 1px。用固定的 `Ut[52]` 置换表还原成 260×160。

### 6.2 测距

滑块图带 alpha 通道：用 alpha 生成掩码，对背景图和滑块图分别做 Canny 边缘检测，
再 `TM_CCOEFF_NORMED` 模板匹配。滑动距离取 `x + 2`，补偿滑块内容的 1px 透明边
和 1px 边界校准。

### 6.3 轨迹

轨迹用 `trajectory_pool.py`：305 条真人轨迹，按终点 3px 分桶，随机取一条，
再做时间 ±2ms、y ±1px、末尾停顿 ±40ms 的微扰动。

这里有一个很重要的认知：

> **轨迹池只解决“轨迹”这一个变量。**
> 如果协议层（w/cookie/challenge）不对，换什么轨迹都会 `forbidden`。

## 7. 最终实现

纯协议版的主流程在 `极验3/极验3.py`：

```python
e_e = generate_e_e()
get_html()                                   # 初始 cookie
challenge, gt = get_challenge()              # register-slide
s = get_one_w(challenge, e_e)                # w1 -> get.php
get_two_w(challenge, gt, s, e_e)             # w2 -> ajax.php（设 cookie）
bg_url, slice_url, s_s, challenge_new = get_pic(challenge, gt)

load_picture(bg_url, slice_url)              # 下载
restore_slider('./bg.jpg', './bg_hy.jpg')    # 312x160 -> 260x160
x, y = get_distance_robust('bg_hy.jpg', 'slice.jpg')

guiji = _pool.get_track(x + 2)               # 轨迹池
guiji.insert(0, [-39, -10, 0])               # 按下偏移
total_time = guiji[-1][2]
get_validate(challenge_new, total_time, x + 2, guiji, s_s, gt, e_e)
```

成功的返回形如：

```json
{"success": 1, "message": "success", "validate": "...", "score": "1"}
```

## 8. 复盘

如果重做一次，我会按这个顺序推进：

1. **先用浏览器做 oracle**：让浏览器跑通，记录每一步的请求、cookie、响应；
2. **再做手动最小闭环**：固定 challenge/s，只验证 w3 + 轨迹，确认加密层没问题；
3. **最后拆纯协议**：一次只替换一个环节，从注册开始，逐步把浏览器行为换成 requests；
4. **用错误码分层**：`fail` 看业务、`forbidden` 看会话/w、`param decrypt error` 看结构、
   `used captcha` 看 challenge 生命周期；
5. **不要过早怀疑轨迹**：轨迹是最后一个变量，不是第一个。

这个项目最大的收获不是“过了一个验证码”，而是学会了：
**把浏览器的隐式状态（cookie、challenge 生命周期、w 的绑定关系）显式地复现出来。**
这件事在别的协议逆向里同样适用。
